## Verdict
  => CRASH REPRODUCED: Apache worker segfaulted processing a GBK-declared
     response whose trailing byte is a valid-but-incomplete GBK lead byte
     (iconv EINVAL, 'incomplete' per the upstream fix description).

## Patched comparison (Apache 2.4.69, target-patched :8081)

Hardened config (ProxyHTMLEnable Off): same gbk/incomplete-fail request returns
the backend's raw bytes unchanged (Content-Type stays charset=gbk, no xml2enc
log lines) - the filter chain never engages, so the vulnerable code path isn't
reached at all. Reachable after: 200.

Patch-only comparison (ProxyHTMLEnable temporarily flipped On to exercise the
fixed mod_xml2enc code directly): same request gives a client-side
"transfer closed with outstanding read data remaining" (curl exit 18), but
`docker top acw3-target-patched` shows the IDENTICAL worker PIDs
(58417/58418/58419) before and after the request - no worker died or was
replaced. Target remained reachable (200) immediately after. This confirms
2.4.69 handles the same input that segfaults 2.4.68 without crashing a worker;
the client-side symptom is a benign side effect of the fix's raw-passthrough
behavior, not a server-side failure.

Verdict: CVE-2026-63686 does not reproduce on the patched target, by either
the config-level mitigation (ProxyHTMLEnable Off) or the code fix itself
(2.4.69 with the filter re-enabled).
